# NInfer A16 resident-weight projection timing

This is a **separate synthetic component diagnostic**. It compares the legacy
`CudaNinferKernels.ProjectA16` helper with the explicit original-schedule A16
candidate. Their F32 summation schedules differ; the tool does not assert that
the two outputs are bit-identical. It does not change serving or the existing
component probe and produces no full-model, quality or end-to-end speed result.

```sh
dotnet build eng/validation/NinferA16TimingProbe/NinferA16TimingProbe.csproj -c Release
dotnet NinferA16TimingProbe.dll --self-test
dotnet NinferA16TimingProbe.dll --execute \
  --legacy-module /absolute/artifacts/qualified/tensorsharp_q35_ninfer.fatbin \
  --candidate-module /absolute/artifacts/qualified/tensorsharp_q35_ninfer_a16.fatbin \
  --legacy-component /absolute/artifacts/legacy-component.json \
  --candidate-component /absolute/artifacts/candidate-component/result.json \
  --out /absolute/artifacts/a16-shape-timing
```

No arguments prints a plan; `--self-test` builds a small CPU fixture and validates
its CPU bounds without loading CUDA. Only `--execute` performs device work. The
operator must hold the exclusive GPU lease, record actual source/runtime/device
identity, and retain the unchanged ggml revision/status. This tool does not start
or stop servers. All output must be in a fresh canonical absolute directory under
ignored `artifacts/` or `docs/validation/`, without symlinked output parents.

Before execution it requires actual passing component certificates for the
**exact module image SHA values** supplied. The candidate certificate must retain
all90 unique fixtures, both module lifetimes, all180 successful records and all
three poison/replay outputs per record. Their original guarded output files are
rehash-checked; a missing, incomplete, failed or mismatched certificate refuses
timing. A certificate for another compiler/module image cannot qualify this one.
External source catalogs still need to bind the helpers, linked CPU oracle,
toolchain, binary and component execution provenance.

The matrix dimensions are actual Qwen target projection dimensions:

| Label | N | K | Synthetic T values |
| --- | ---: | ---: | --- |
| gate-up | 34816 | 5120 | 1,2,3 |
| down | 5120 | 17408 | 1,2,3 |
| output | 5120 | 6144 | 1,2,3 |
| attention-input | 14336 | 5120 | 1,2,3 |

These are synthetic matrices, not the model's weight values. Not every listed
role/T combination necessarily uses A16 in serving: its role-specific A4 policy
can select another path. Original BF16 exception projections are outside this
NVFP4 timing experiment. Synthetic throughput cannot be multiplied by a layer
count to invent whole-model latency.

CPU references and allocations are prepared outside event intervals. For each
shape/T, **every resident weight copy** is evaluated before timing. The candidate
must match the original-layout, original-schedule CPU oracle's unrounded F32 bits
at every output element. Both paths must satisfy the predeclared FP64 bound:

`abs(output-ideal) <= gamma_(K/32+16)*sum(abs(code*scale*inverseD*input))`,
with `gamma_n=n*u/(1-n*u)` and `u=2^-24`. Inputs are finite BF16-representable
values; output row padding is poisoned. Full output finiteness, bounds, replay
bits and prefix/suffix/stride guards are checked before and after measured
batches. Original weight/input allocations are read back in full and must remain
unchanged. The exact gate applies to the candidate's declared arithmetic, not to
legacy-versus-candidate equality.

There are five A/B/B/A blocks for each shape/T/cache label. A is legacy and B is
candidate. Every arm has separate unmeasured warmup calls and one CUDA-event
batch. The recorded denominator is the actual number of projections in that
batch. CPU oracle work, allocation, HtoD setup, output poisoning, warmups, DtoH
readback, validation and file writing are outside the interval. Driver enqueue
gaps and device scheduling inside the stream interval are not isolated hardware
kernel-counter measurements.

Two cache labels remain separate:

- `warm-repeat-address`:16 projections repeatedly use one weight allocation.
  Some matrices fit approximately within the 5090's L2. A large warm speedup
  cannot be presented as a full-model gain.
- `rotation-over-2L2-addresses`: distinct resident weight allocations have an
  address footprint strictly greater than twice the **queried actual L2 size**.
  Each interval traverses the same complete address sequence twice on both
  paths. There is no timed or hidden cache-flush operation. This is a controlled
  working-set rotation, **not verified physical cold cache or a measured cache
  miss rate**; data compression, replacement and other cache behavior remain
  unmeasured.

All weights are already resident during timing. Random encoded matrices are
deterministically generated by the source-pinned xorshift scheme, and the exact
original/converted weight SHA values and sizes are recorded. Full synthetic
weight files are not saved again; the reusable generator reproduces them. Actual
input vectors, full CPU F32 references, FP64 ideal/bounds, every original device
validation output and every timed-arm guarded output are retained. The report
also records module images, assembly hashes, actual driver/device/L2 information
and component certificate hashes. GPU UUID/clock/power telemetry and global
exclusive-execution evidence belong to the external controller.

The ratios are descriptive medians of ten intervals per path/cache/profile, with
their ranges. The order is counterbalanced rather than randomized; no statistical
significance, device-counter bottleneck, quality equivalence, or end-to-end
improvement follows. Model adoption still requires separate actual model quality
and end-to-end ABBA evaluation.
