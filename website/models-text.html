Text & LLM Models

Copy-paste download and run recipes for every text architecture, followed by per-family capability notes for image, audio and PDF input, thinking mode, and tool calling.

Embedding models: Snowflake Arctic Embed L v2.0, MiniLM, and EmbeddingGemma 2 with text and optional image/audio/video input. Serve normalized vectors through --embeddings and OpenAI/Ollama APIs; backend support depends on the encoder. Models, APIs, and validation →

Download & run, per family

Install and verify the .NET 10 SDK for your platform before running a build command. The first block is the verified Gemma 4 E4B quick start. All blocks use the Hugging Face CLI (pip install -U huggingface_hub); the per-family blocks after the first assume a full source build from the repository root. One-shot CLI text prompts are read from a file via --input (put your question in prompt.txt first — --prompt is reserved for the image- and video-generation models). Swap --backend for ggml_metal / ggml_vulkan / ggml_cpu to match your hardware (the CLI default is ggml_cpu).

Quick start — Gemma 4 E4B Q8_0 (native GGML)

Allow time for the 7.48 GiB download and first restore/build; duration depends on your connection and machine. This example uses the E4B Q8_0 family; the linked ggml-org repository is the recommended public source. This block is for Linux + NVIDIA:

hf download ggml-org/gemma-4-E4B-it-GGUF gemma-4-E4B-it-Q8_0.gguf --local-dir models
TENSORSHARP_GGML_NATIVE_ENABLE_CUDA=ON dotnet build TensorSharp.slnx -c Release -p:TensorSharpSkipMlxNative=true
echo "Explain why local inference is useful." > prompt.txt

# Text needs no mmproj.
dotnet run --project TensorSharp.Cli -c Release --no-build -- --model models/gemma-4-E4B-it-Q8_0.gguf \
    --input prompt.txt --max-tokens 300 --backend ggml_cuda
dotnet run --project TensorSharp.Server.Host -c Release --no-build -- --model models/gemma-4-E4B-it-Q8_0.gguf \
    --backend ggml_cuda

On Apple Silicon, omit the CUDA environment assignment and use ggml_metal; on a supported Windows/Linux Vulkan GPU, request TENSORSHARP_GGML_NATIVE_ENABLE_VULKAN=ON instead and use ggml_vulkan. For image, video, or audio input, also run hf download ggml-org/gemma-4-E4B-it-GGUF mmproj-gemma-4-E4B-it-Q8_0.gguf --local-dir models and pass --mmproj models/mmproj-gemma-4-E4B-it-Q8_0.gguf. The server's browser UI is http://localhost:5000/; its liveness endpoint is /health. See Getting Started for Windows PowerShell and full platform syntax.

DeepSeek V4.1 Flash 1017 (text, image/video, thinking, tools)

DeepSeek V4.1 has a dedicated graph with compressed attention, an indexer, hyper-connections and embedded Engram features; it is not V4 with renamed weights. The latest selected conversion is unsloth/DeepSeek-V4.1-Flash-1017-GGUF UD-IQ2_XXS, six shards, Hugging Face revision 60ad3651. Use the current model card for exact filenames, conversion qualifications, launch settings and backend limits rather than an older checkpoint's numbers.

ggml_cuda is the serving backend. --tp N and --layer-split N are different local placement modes; their throughput depends on the checkpoint and interconnect. The managed cpu executor is a correctness/portability path, with a small synthetic PyTorch-oracle gate rather than a full-checkpoint CPU quality qualification. Images and video need the matching vision companion; audio is refused.

Recorded 2026-10-22–23 on five A40s: at a ~1.8K-token prompt, TP5 exact prefill is 563.9 tok/s against llama.cpp layer split 174.6 (3.23×); the default approximate YOCO path is 960.5 (5.50×). Context is 32,768, concurrency 1, output 256 tokens, greedy and thinking off; medians of three after warmup. This is internal prefill timing, not client TTFT. Approximation has a measured quality cost: perplexity 2.4978 vs exact 2.4811 and llama.cpp 2.4697. Both prompt lengths, exact/approximate results and limits →

DeepSeek V4 Flash (284B MoE, text, thinking, tools, DSpark)

A 284B mixture-of-experts model with a 128-token raw sliding window plus block-compressed attention (1M advertised context). It does not use the generic per-op forward: TensorSharp runs it through one of three dedicated whole-model executors — --backend cuda (direct CUDA, no ggml), --backend ggml_cuda / ggml_vulkan (native ggml), and --backend cpu (100% pure C#, no native dependencies). The GPU executors use --layer-split N to place whole layers across N local GPUs, allowing models larger than one card to run. Without a placement configuration they use one device; the CPU executor streams weights from the mapped shards.

# ~160 GB of weights for the Q8 tier — pick a smaller quant directory if that is too much
hf download unsloth/DeepSeek-V4-Flash-0731-GGUF --include "UD-Q8_K_XL/*" --local-dir models
hf download bleysg/DeepSeek-V4-Flash-DSpark-drafter-GGUF DSpark-drafter-Q2K-Q8-0731.gguf --local-dir models

# Plain decode — point --model at the FIRST shard
dotnet TensorSharp.Cli/bin/TensorSharp.Cli.dll \
    --model models/UD-Q8_K_XL/DeepSeek-V4-Flash-0731-UD-Q8_K_XL-00001-of-00005.gguf \
    --backend ggml_cuda --layer-split 4 --input prompt.txt --max-tokens 200

# DSpark block speculative decoding (~1.3-1.4x decode, measured with greedy sampling)
dotnet TensorSharp.Cli/bin/TensorSharp.Cli.dll \
    --model models/UD-Q8_K_XL/DeepSeek-V4-Flash-0731-UD-Q8_K_XL-00001-of-00005.gguf \
    --backend ggml_cuda --layer-split 4 --draft-model models/DSpark-drafter-Q2K-Q8-0731.gguf \
    --input prompt.txt --max-tokens 200 --temperature 0

# Served over HTTP, 4 GPUs, with speculation on
dotnet TensorSharp.Server.Host/bin/TensorSharp.Server.Host.dll \
    --model models/UD-Q8_K_XL/DeepSeek-V4-Flash-0731-UD-Q8_K_XL-00001-of-00005.gguf \
    --backend ggml_cuda --layer-split 4 --draft-model models/DSpark-drafter-Q2K-Q8-0731.gguf

DSpark drafts a whole block of tokens per step and the trunk verifies the block in one batched forward, so greedy output is unchanged. On the CLI and the server alike every verify row is drawn with the run's or request's own sampler, so it composes with any sampling settings; under repetition, presence or frequency penalties acceptance falls, because the drafted block is not penalized. See DSpark speculative decoding.

GLM 5.x (744B-A40B MoE, text, thinking, tools)

A 744B mixture-of-experts model — 256 routed experts at top-8 plus one shared expert — built on DeepSeek Sparse Attention: Multi-head Latent Attention with weight absorption, so the cache is one 576-wide row per token per layer, plus a "lightning indexer" that decides which cached tokens each query may attend to (1M advertised context). Like DeepSeek V4 it skips the generic per-op forward: --backend ggml_cuda / ggml_vulkan / ggml_cpu / ggml_metal run a native whole-model ggml executor that accepts --layer-split N on CUDA or Vulkan to place 226 GiB of weights across N local GPUs (default: one device), while --backend cpu (100% pure C#, no native dependencies) and --backend cuda run the managed per-op path. MLX does not run it. The multi-shard GGUF is read by GgufFile itself, so --model points at the first shard. The commands below are GLM-5.2's; GLM-5.3 (not Flash) shares the same glm-dsa loader and gets its own block after them.

# ~226 GiB for the UD-IQ2_XXS tier (6 shards) — pick a different quant directory for more or less
hf download unsloth/GLM-5.2-GGUF --include "UD-IQ2_XXS/*" --local-dir models

# Explicit local layer split on 3x96 GB GPUs — point --model at the FIRST shard
dotnet TensorSharp.Cli/bin/TensorSharp.Cli.dll \
    --model models/UD-IQ2_XXS/GLM-5.2-UD-IQ2_XXS-00001-of-00006.gguf \
    --backend ggml_cuda --layer-split 3 --input prompt.txt --max-tokens 200

# Thinking mode, interactive
dotnet TensorSharp.Cli/bin/TensorSharp.Cli.dll \
    --model models/UD-IQ2_XXS/GLM-5.2-UD-IQ2_XXS-00001-of-00006.gguf \
    --backend ggml_cuda --layer-split 3 --interactive --think

# Not enough VRAM? Keep the routed experts of the first N layers in system RAM
dotnet TensorSharp.Cli/bin/TensorSharp.Cli.dll \
    --model models/UD-IQ2_XXS/GLM-5.2-UD-IQ2_XXS-00001-of-00006.gguf \
    --backend ggml_cuda --layer-split 3 --n-cpu-moe 30 --input prompt.txt --max-tokens 200

# Served over HTTP
dotnet TensorSharp.Server.Host/bin/TensorSharp.Server.Host.dll \
    --model models/UD-IQ2_XXS/GLM-5.2-UD-IQ2_XXS-00001-of-00006.gguf \
    --backend ggml_cuda --layer-split 3

The advertised 1M-token context is a ceiling, not a promise: 1M tokens of MLA cache is about 93 GiB, so once the weights land the loader asks the devices how much VRAM is actually free, sizes the context to what fits alongside one full prefill graph, and logs what it picked. On 3× RTX PRO 6000 with GLM-5.2 that is 342,272 tokens on the plain layer split, 646,400 with --n-cpu-moe 30, and 91,136 under --tp 3 (every rank holds a full-length cache). Set MAX_CONTEXT to make a specific length a hard requirement instead — it is honoured if it fits and refused with the numbers if it does not.

--tp N works here too, but on PCIe-attached cards it is a capacity feature rather than a speed one: the two all-reduces every one of the 78 layers needs cost more bus time than the split saves, so with GLM-5.2 --tp 3 measures pp2048 505.6 / tg64 17.6 tok/s against 915.9 / 43.9 on the layer split. Concurrency is served by native per-sequence slots (each request owns its MLA and indexer caches), with a default-on batched fused decode worth 1.81× aggregate at 4 concurrent requests (measured on GLM-5.2); set TS_BATCHED_FUSED_DECODE=0 to disable it. See Tensor parallelism and Continuous batching.

GLM-5.3 (not Flash) is the same glm-dsa block shape as GLM-5.2 — 79 blocks (78 trunk + one NextN), 256 routed experts at top-8 plus one shared expert, MLA with the lightning indexer, rope base 8e6 — so it loads on the GLM-5.2 path with no new code and no new flag: one architecture descriptor serves GLM-5.2, GLM-5.3 and GLM-5.3-Flash, and Flash versus non-Flash is a single boolean on general.architecture. unsloth/GLM-5.3-GGUF keeps one subdirectory per quant, each a multi-shard set — UD-Q2_K_XL is seven shards, 236.4 GiB. It is text only twice over: the repository publishes no mmproj at any quant, and an --mmproj handed to glm-dsa is warned about and ignored rather than refused, so the result is a text-only run and not a failure. --spec loads the complete NextN block at blk.78, but that block ships no nextn.shared_head_head.weight and borrows the trunk LM head, which is column-parallel under --tp — so speculation is engaged on single-device or explicit --layer-split N placement (no active tensor parallelism), and the flag has to be on the command line before the model loads.

# ~236.4 GiB for the UD-Q2_K_XL tier (7 shards) — pick a different quant directory for more or less
hf download unsloth/GLM-5.3-GGUF --include "UD-Q2_K_XL/*" --local-dir models

# Explicit local layer split on 8x46 GB GPUs — point --model at the FIRST shard
dotnet TensorSharp.Cli/bin/TensorSharp.Cli.dll \
    --model models/UD-Q2_K_XL/GLM-5.3-UD-Q2_K_XL-00001-of-00007.gguf \
    --backend ggml_cuda --layer-split 8 --input prompt.txt --max-tokens 200

# NextN speculation — use explicit layer split here, with no active tensor parallelism
dotnet TensorSharp.Server.Host/bin/TensorSharp.Server.Host.dll \
    --model models/UD-Q2_K_XL/GLM-5.3-UD-Q2_K_XL-00001-of-00007.gguf \
    --backend ggml_cuda --layer-split 8 --spec

Measured on 8× A40 46 GB without NVLink, GLM-5.3 UD-Q2_K_XL, a 10,531-token prompt, 300 decode tokens, median of three, whole-layer placement: prefill 251.6 t/s, decode 20.48 t/s and a 264 s load, against llama.cpp's 20.28 t/s decode and 753 s load on the same box — a decode tie with a 2.9× faster load of a 236.4 GiB checkpoint. The honest gap is time to first token: 41.9 s against 29.0 s, about 1.4× slower (that llama.cpp cell recorded no prompt-token count, so no prefill tok/s is reported for it). --tp N is accepted here but local / single-process only, and it has never been run on GLM-5.3: every rank would hold a full replicated KV cache, and the only recorded arithmetic is a non-fit — --tp 8 wants 41.7 GiB per rank against 46 GB cards. --tp-node-id / --tp-peers are refused for the whole GLM family before the model is built. Both releases share the GLM model card.

GLM-5.3-Flash (320B MoE, text + image, thinking, tools)

The hybrid successor loads through the same native whole-model ggml executor and the same model class as GLM-5.2 — its GGUF architecture id is glm5next — with four architectural changes layered on top. 320B parameters, 288 routed experts at top-8 plus one shared, 46 blocks = 45 trunk + 1 NextN. KDA linear attention runs on 34 of the 45 trunk layers; the other 11 are NoPE MLA + DSA (no rope anywhere in the text tower, the 512-wide latent is the cache row); the indexer is pooled — 4-cell pools, top-k 2048 taken over pools and then expanded to their members; hyper-connections are Sinkhorn over ×4 streams; and every SwiGLU is clamped at limit 10. The KDA recurrent state cannot be rewound, so a cached prefix is reused only when the new prompt extends it exactly.

# ~101 GiB for the UD-Q2_K_XL tier — pick a different quant directory for more or less
hf download unsloth/GLM-5.3-Flash-GGUF --include "UD-Q2_K_XL/*" --local-dir models
hf download unsloth/GLM-5.3-Flash-GGUF mmproj-BF16.gguf --local-dir models

# Explicit local layer split on 2x96 GB GPUs — point --model at the FIRST shard
# (N is however many shards the quant directory you downloaded holds)
dotnet TensorSharp.Cli/bin/TensorSharp.Cli.dll \
    --model models/UD-Q2_K_XL/GLM-5.3-Flash-UD-Q2_K_XL-00001-of-0000N.gguf \
    --backend ggml_cuda --layer-split 2 --input prompt.txt --max-tokens 200

# Image understanding — the GLM-OCR ViT ships as mmproj-BF16.gguf
dotnet TensorSharp.Cli/bin/TensorSharp.Cli.dll \
    --model models/UD-Q2_K_XL/GLM-5.3-Flash-UD-Q2_K_XL-00001-of-0000N.gguf \
    --mmproj models/mmproj-BF16.gguf --image photo.png --input question.txt \
    --max-tokens 300 --backend ggml_cuda --layer-split 2

# Not enough VRAM? Keep the routed experts of the first N layers in system RAM
dotnet TensorSharp.Cli/bin/TensorSharp.Cli.dll \
    --model models/UD-Q2_K_XL/GLM-5.3-Flash-UD-Q2_K_XL-00001-of-0000N.gguf \
    --backend ggml_cuda --layer-split 2 --n-cpu-moe 10 --input prompt.txt --max-tokens 200

# Served over HTTP
dotnet TensorSharp.Server.Host/bin/TensorSharp.Server.Host.dll \
    --model models/UD-Q2_K_XL/GLM-5.3-Flash-UD-Q2_K_XL-00001-of-0000N.gguf \
    --mmproj models/mmproj-BF16.gguf --backend ggml_cuda --layer-split 2

What runs today: the whole-layer placement across N GPUs with --layer-split N, --cpu-moe / --n-cpu-moe N host-resident experts, per-sequence native slots for serving, and vision — --image, multi-image prompts and multi-turn image sessions, through the GLM-OCR ViT. On GGML GPU backends, --tp N selects native local/single-process tensor parallelism, as it does for GLM-5.2: KDA/MLA heads and routed-expert hidden rows are sharded, and KDA recurrent state is per-rank. With full sharding on one rank per local GPU, no CPU MoE or tracing, and native hyper-connection kernels, segmented rank-local graphs submit concurrently: routed-MoE partials reduce first, then every rank computes and adds its replicated shared expert locally before Sinkhorn hyper-connections; hyper-connections, pooled indexer, router, norms, dense layers and embedding remain unsharded and execute per rank, while output norm / LM head stay on rank 0. CPU MoE, tracing, partial sharding, oversubscription, or missing native hyper-connection kernels select the combined scheduler fallback, where the shared expert runs once on rank 0. The native TP path for both GLM-5.2 and GLM-5.3-Flash is local/single-process, not distributed or cross-node. Not yet: NextN/MTP speculation.

Measured on 2× RTX PRO 6000 Blackwell (96 GB) with GLM-5.3-Flash-UD-Q2_K_XL (101 GiB), layer split, both engines at n_ubatch 2048, back to back: pp2048 2070 t/s for llama.cpp against 2014 for TensorSharp, pp16384 1690 against 1692, pp32768 1483 against 1446, and tg64 36.6 against 73.5. Prefill is within a few percent either way; decode runs at 2.0× llama.cpp.

It runs on --backend cpu too — the 100% pure-C# path, no native dependencies — now that glm5next's NoPE MLA (no rope half anywhere, so nothing to split off) and its IQ2_XS / IQ4_XS weights have managed support. It is well behind the GGML backends there: on a 122-CPU box (22-token prompt, 16 tokens out) it measures prefill 3.1 / decode 1.6 tok/s against ggml_cpu's 17.7 / 3.9 on the same file and box — about 5.7× off on prefill and 2.4× on decode, with roughly 89% of the time in the MoE expert path. Treat it as a reference implementation to A/B against rather than a bit-parity one: the prefill-logit cosine against ggml_cpu is 0.9567 over the 154880-wide vocabulary and the greedy text differs, because native's top two logits are 0.11 apart and the managed path ranks them the other way. That is consistent with 2-bit expert-pick sensitivity, but it is not proven to be only that — 0.96 is lower than the ~0.999 a higher-precision checkpoint would be expected to give, and no higher-precision GLM-5.3-Flash GGUF was available as a control. The measurements, the four fixes it took, and the caveat in full are in the GLM model card.

Qwen 3.8 Flash Next (hybrid MoE, text + image/video, thinking, tools, MTP head)

A hybrid mixture-of-experts model whose GGUF architecture id is qwen4exp: GatedDeltaNet recurrent layers interleaved with full-attention layers (some behind Qwen Sparse Attention's indexer), a PLE n-gram embedding block, ×4 hyper-connection streams and a 512-expert MoE. 48 layers, hidden size 2560, 24 query / 2 KV heads at head_dim 256, a 248,320-token vocabulary, 10 of the 512 experts used per token, GDN on 36 of the 48 layers and PLE on layer 1. On the GGML backends the whole token runs as (almost) one graph — embedding, in-graph PLE, all 48 layers, the final mixer and the LM head — replayed from a shape-keyed cache of captured graphs. Vision rides the Qwen3.5-VL tower with (T,H,W) IMRoPE positions, so multi-image prompts and multi-turn image sessions both work. A cached prefix is reused only when the new prompt extends it exactly (the GDN recurrence cannot rewind), and in the radix prefix cache that reuse stops at the conversation's first image or video span: a later turn restores at most a checkpoint that ends before the attachment, typically the system prompt, and re-prefills the rest. Concurrent requests are served through per-sequence state holders — each request owns its attention KV and indexer caches, its GDN and PLE state — so switching between them is a reference swap. Thinking is switchable, as on Qwen 3.5: --think / "think": true opens the <think> block, and without it the published template renders a closed, empty one.

🧰

Tool status: qwen4exp returns structured tool calls through the Qwen 3.5 parser — a <tool_call> block with an XML <function=…><parameter=…> body or a JSON one, streamed or with thinking on — so client tools, the built-in Agent Skills and code-execution tools, and sub-agent delegation on the server are all offered to it. On three A40s with UD-IQ4_XS (2026-09-19) all 12 generic tool-call cases passed, each completing a tool-result round trip; the model card records the skill/shell/code workflow results and the cases that still fail.

Local CUDA tensor parallelism is now available. --tp N on ggml_cuda splits routed/shared FFN intermediate channels and output rows, using FP32 gathers to preserve down-projection reduction order; attention, GDN, QSA and PLE weights/state stay replicated. The loader checks the degree, quantization and exact-strip kernel layout before bulk loading. Physical-device qualification covers UD-IQ4_XS on NVIDIA A40 TP2/TP4; UD-Q2_K_XL's IQ2_XS/IQ3_XXS FFNs and floating-point FFNs are refused under TP. Prefix checkpoints remain disabled in this mode. --layer-split N remains a separate GGML CUDA/Vulkan option, including for UD-Q2_K_XL; the direct cuda engine uses layer split. Do not combine the modes; multi-node groups are unsupported. The older 2× A100 UD-Q2_K_XL measurements concern layer split: identical greedy output, 24.2 + 26.2 GB VRAM, and about 1520–1550 prefill / 56 decode tok/s. They do not measure the new TP path. Quantization constraints, parity and timing scope →

Speculative decoding uses a separate shared MTP head, not tensors in the trunk (the published Q8_0 shards carry no nextn/mtp tensors): --draft-model mtp-Qwen3.8-Flash-Next-shared-Q8_0.gguf (2,786,568,256 bytes; unsloth/Qwen3.8-Flash-Next-GGUF at revision 38bb39ee) attaches it on a GGML backend. It drafts only for a solo request that prefilled from position 0; turns that continue a retained holder or a shared-prefix clone decode plainly. Measured on UD-Q2_K_XL over a three-GPU A40 layer split with --spec-draft 3, a 192-token code-copy stream was identical to plain greedy at 1.69× plain decode (83.2 against 49.1 tok/s) with the current verify-row kernels, which make every verify row bit-identical to its decode step (1.75–1.96× before that change on 2026-09-17), but prose does not pay: 512-token answers decoded at 44–46 tok/s against 52 plain. See the model card.

Larger than memory. UD-Q2_K_XL is 78.9 GB (73.4 GiB), but a token reads only 16 rows of its 28.8 GB n-gram table and 10 of each layer's 512 experts, so TensorSharp runs it on machines that cannot hold it. On ggml_metal the n-gram table stays in the GGUF memory mapping and a token's rows are read on demand; unless --n-cpu-moe N or --cpu-moe is given, the engine also plans the expert offload, keeping whole layers' experts on the GPU while they fit and running the first layers' on the host from the same mapping, where the page cache holds the hot ones and the rest come from the SSD as tokens need them. On an M5 Pro with 48 GB (33 of the 48 layers' experts on the host), a 1,818-token prompt with 256 greedy tokens measured 109.4–115.5 prefill / 12.8–12.9 decode tok/s against 20.4–22.4 / 13.00–13.24 for llama.cpp with -ngl 0 -t 12 (28.8–31.6 / 11.94–12.48 with --no-op-offload), whose full GPU offload runs out of memory there. --backend mlx is refused up front: MLX has no kernels for the sparse-attention indexer, the hyper-connections, the n-gram table or the IQ2_XS/IQ3_XXS experts. The direct cuda engine runs those experts: on 2× A40 with --layer-split 2, warm, the same prompt measured 1,612–1,613 / 56.85–56.93 tok/s (ggml_cuda: 1,174–1,217 / 52.9–53.1) against llama.cpp's 752–963 / 59.04–59.86. TensorAgent offers the file on 48 GB Macs; see the model card.

Ternary-Bonsai-2-27B-PQ2_0.gguf and -PTQ1_0.gguf declare general.architecture = qwen35 — 64 layers, 48 GatedDeltaNet and 16 full attention — and add PRISM signed-Hadamard metadata (prism.hadamard.*) and the publisher tensor types PQ2_0 (142) and PTQ1_0 (143). Muse Spark (816B sparse MoE, text + image, thinking, tools)

Unsloth's Muse-Spark-Open-816B-A42B declares general.architecture = muse-spark (alias muse_spark): 816B parameters with about 42B active per token, 62 blocks at hidden width 8192, 128 query / 16 KV heads at head dim 64, and 256 routed experts with top-8 sigmoid routing and a 4096-wide expert latent. 46 layers use a 2048-token sliding window with RoPE; the other 16 are global NoPE layers. The metadata advertises 1,048,576 tokens of context, which is not validated: without MAX_CONTEXT the native executor caps the context to the largest size that fits and logs it, and with MAX_CONTEXT set a size that does not fit is refused. This is a multi-GPU server model: the measured setup is ten A40s (46 GB each) holding every expert of the UD-IQ3_XXS quant in GPU memory; on fewer GPUs, the expert stacks that do not fit go to host memory, which then has to be large. It is not in the TensorAgent catalog.

# UD-IQ3_XXS is 8 shards, 317 GiB (UD-Q3_K_XL is 10, UD-Q4_K_XL 12) — keep every shard of a quant in one directory

# Image projector (2.2 GB), at the repository root

# The measured profile: ten A40s, every expert in VRAM, 32K context, five planned slots — --model takes any shard of the set
MAX_CONTEXT=32768 TS_MUSE_SPARK_PLAN_SLOTS=5 TS_CODE_EXEC=0 \
dotnet TensorSharp.Server.Host/bin/TensorSharp.Server.Host.dll \
    --model models/muse-spark/UD-IQ3_XXS/Muse-Spark-Open-816B-A42B-UD-IQ3_XXS-00001-of-00008.gguf \
    --backend ggml_cuda --layer-split 10 \
    --host 127.0.0.1 --port 8083 --no-webui --no-skills --no-multi-agent
# --tp 10 instead of --layer-split 10 splits every layer over the ten GPUs: faster decode, slower long-prompt prefill

Later shards are not standalone models; TensorSharp reads shard 1 for the architecture, tokenizer and settings and loads the tensors from the complete set. --no-webui --no-skills --no-multi-agent match the benchmark run — drop them to serve the Web UI, Agent Skills and sub-agents. Five planned slots cover four concurrent requests plus the shared-prefix checkpoint. For image input add --mmproj models/muse-spark/mmproj-Q8_0.gguf, with TS_MUSE_SPARK_DEV0_RESERVE_MB leaving room on GPU 0 for the vision encoder (the ten-A40 run loaded no projector). With fewer GPUs, TS_MUSE_SPARK_CPU_MOE=auto holds the expert stacks that do not fit in host memory.

On ggml_cuda and ggml_vulkan it runs by default through a TensorSharp-owned native whole-model executor that loads the split GGUF itself and submits one GGML graph per micro-batch (2048-token prefill micro-batches) across every GPU and the CPU, on unchanged upstream ggml. --layer-split N spreads the 62 layers over N GPUs, up to 16, filling them evenly (a count it cannot honour is refused rather than run on fewer GPUs), and TS_MUSE_SPARK_CPU_MOE=auto places each layer's gate, up and down expert stacks separately, keeping as many on the GPUs as fit and as few bytes as possible on the host. It overrides --n-cpu-moe N, which instead forces the first N layers' experts to the host; without either, a model that does not fit is refused with a message that names the option. On a multi-socket host the host expert stacks are copied into NUMA-local memory and run by pinned worker threads, and a TensorSharp static-row kernel runs 2–16-token batches with results bit-identical to ggml's. TS_MUSE_SPARK_NATIVE=0 selects the older per-op path, and TS_MUSE_SPARK_NATIVE=1 opts the GGML CPU backend into the executor. The full-model measurements are on ggml_cuda only: Vulkan selects the executor by default but has no recorded full-model run.

On two or more CUDA GPUs with every expert in GPU memory, a layer split pipelines prefill: each prompt call is cut into equal micro-batches, and GPU k works on one while GPU k+1 works on the one before, as llama.cpp's pipeline parallelism does. The micro-batch is sized per call — about a quarter of it, between 512 and 2,048 rows, smaller where a long context's masks would not fit the staging buffer — unless TS_MUSE_SPARK_PIPELINE_UBATCH fixes it; TS_MUSE_SPARK_PIPELINE=0 turns pipelining off and 1 requires it, and the load log says which applies. When a prompt is alone, the scheduler lets the model size its prefill steps — 8,192 tokens, a short remainder joined to the step before — unless TS_SCHED_SOLO_PREFILL_CHUNK is set. In the measured ten-A40 run the layer split held about 36 GiB per GPU and loaded in about 6 minutes.

On ggml_cuda, --tp N runs the same native executor as tensor parallelism: every layer is split over the first N CUDA GPUs (choose them with CUDA_VISIBLE_DEVICES) through upstream ggml's meta backend, the mechanism behind llama.cpp's -sm tensor. Attention is divided by KV group, routed experts along their hidden dimension and the output head by vocabulary rows, and each layer ends in two all-reduces; TensorSharp probes peer copies first and runs NCCL over shared memory where P2P is broken. Every expert must fit in GPU memory, so --n-cpu-moe N is refused; so are TS_MUSE_SPARK_LAYER_SPLIT, TS_MUSE_SPARK_PIPELINE=1 and N above the 16 KV heads, and pipelined prefill and speculation are off. TS_MUSE_SPARK_NATIVE=0 keeps the older per-op TP path, which --tp N on ggml_vulkan also uses: it shards attention by GQA head groups, partitions experts whole, accepts uneven partitions (nine GPUs, for example) and is single-node only.

Each request gets an F16 per-sequence KV slot — a ring buffer for the sliding layers, lazily grown rows for the global ones — and decode is batched across slots for text and image requests, as is the prefill of new text prompts that arrive together. The prefix cache continues a conversation from its finished slot, rewinds a finished conversation for a regenerated answer, and clones a shared system-prompt / template-preamble checkpoint into new conversations; unrelated conversations share only that public prefix.

Images arrive as OpenAI image_url parts or CLI --image, through the shared Muse-Glimmer vision encoder and the release's own mmproj-Q8_0.gguf; a Muse-Glimmer-30B projector is rejected, and there is no audio input. Thinking and tools follow the Muse-Glimmer channel protocol: the model reasons in an assistant to=self message and answers in assistant to=user, the template renders a reasoning level (low / medium / high / xhigh), and ATEM XML tool calls are routed on the to= recipient header, with a commentary channel besides — so Agent Skills get full progressive disclosure and sub-agents are offered. response_format combines with "think": true: the JSON grammar arms after to=user<|message|>. The model needs the GGUF's embedded chat template; there is no generic fallback. Speculation is the weight-free n-gram drafter only (--spec --spec-type ngram) — there is no learned drafter.

Report refreshed 2026-10-22; measurement date unrecorded: ten A40s, UD-IQ3_XXS, all experts in VRAM, 32,768 context, F16 KV and thinking off. Layer-split prefill at 4,075 prompt tokens is 999.7 vs 483.2 tok/s (2.07×, one request, output cap 32); tensor-parallel solo decode is 22.63 vs 16.19 tok/s (1.40×, 167-token prompt, output cap 256), and four-request aggregate output is 45.73 vs 24.49 (1.87×). Reference llama.cpp modes match; reference TP rows use only two repeats. The host has no working P2P and the reference build has no NCCL. A TensorSharp-owned native whole-model executor loads the split GGUF itself and submits one GGML graph per micro-batch on unchanged upstream ggml. --layer-split N places whole layers on up to 16 GPUs and pipelines a prompt's prefill across them; --n-cpu-moe N serves layers 0..N-1's routed experts from system RAM (layers 0-2 are dense), and TS_MINIMAX_M3_CPU_MOE=auto places only the stacks that do not fit. --tp N runs the executor on upstream ggml's meta backend over the first N CUDA GPUs: with only four KV heads, attention, the indexer and the caches are mirrored on every GPU while the FFNs split, so each GPU holds less context (45,824 tokens on eight A40s), and host experts and the drafter are refused. Thinking / reasoning mode

Thinking-capable models (Qwen 3.5/3.6, Qwen 3.8 Flash Next, Gemma 4, GPT OSS, Nemotron-H, DeepSeek V4, DeepSeek V4.1, GLM 5.x, Muse-Glimmer, Muse Spark, MiniMax-M3.1) produce structured chain-of-thought before the final answer. The thinking content is separated from the visible response so the client can show or hide it.

  • Qwen 3.5/3.6 / Nemotron-H — <think>…</think> tags. With thinking off, Nemotron-H Reasoning-128K sometimes reasons past its closed <think></think> and closes the block itself. When the close starts within the reply's first 2,048 characters, that text is reported as reasoning, not as the answer; a later close counts as answer text, so the reasoning and the literal </think> stay in the answer, a known limitation (details).
  • Qwen 3.8 Flash Next — the same <think>…</think> tags and the same switch: with thinking off, the published template renders a closed, empty <think></think> block.
  • Gemma 4 — <|channel>thought …<channel|> tags.
  • GPT OSS — Harmony format: <|channel|>analysis for thinking, <|channel|>final for the answer.
  • DeepSeek V4 — <think>…</think> tags; the chat template closes the block immediately unless thinking is requested, so reasoning is opt-in.
  • DeepSeek V4.1 — the same tags, with a trained closing transition: at TS_THINKING_BUDGET the model emits </think> and finishes the answer inside the original max_tokens. The budget defaults to 75% of the output allowance when that allowance is at least 512 tokens.
  • GLM 5.x — <think>…</think> tags, also opt-in: --think adds a Reasoning Effort: Max system line and leaves the block open for the model to close, and without it the prompt emits an empty <think></think>. Earlier turns' reasoning is always dropped from the prompt. GLM-5.3-Flash always reasons: its system line maps reasoning_effort: "low" / "high" to Low / High, with Max for omitted or "medium" effort, the generation prompt always opens <think>, and past turns keep their reasoning.
  • Muse-Glimmer — an assistant to=self reasoning channel emitted by the chat template.
  • Muse Spark — the same channel protocol: reasoning in an assistant to=self message, the answer in assistant to=user. The template also renders a reasoning level (low / medium / high / xhigh).
  • MiniMax-M3.1 — <mm:think>…</mm:think>, adaptive: the template has no switch, so the model decides each turn; "think": true opens the block in the prompt, and reasoning cannot be turned off. reasoning_effort (low / medium / high) is rendered as <effort>.
  • DiffusionGemma — not prompted: prompts always render with thinking off. A thought block the model writes anyway is parsed out and returned as reasoning only with "think": true.

Enable it via --think (CLI), "think": true (Ollama API / Web UI), or the thinking toggle in the browser. Responses expose the reasoning separately — e.g. message.thinking in the Ollama chat response.

Tool calling / function calling

Supported model families can invoke user-defined tools and participate in multi-turn tool-call conversations. Define tools as JSON and pass them via --tools (CLI) or the tools parameter (API). Each supported architecture uses its own wire format, and its output parser extracts calls into structured tool_calls:

  • Nemotron-H — Reasoning-128K: the Nemotron family convention, <TOOLCALL>[{"name": …, "arguments": {…}}]</TOOLCALL> (Python-style calls such as [read_file(path="notes.txt")] are accepted too). Nemotron 3 Nano / Omni: <tool_call> with an XML <function=NAME><parameter=key> body (the JSON form is still accepted).
  • Qwen 3.5 / 3.6, Qwen 3.8 Flash Next — the same <tool_call> block with an XML body: <function=NAME><parameter=key>value</parameter></function> (the JSON form is still accepted).
  • Gemma 4 — <|tool_call>call:function_name{args}<tool_call|>
  • GPT OSS (Harmony) — tools declared as a TypeScript namespace; calls emitted on the commentary channel.
  • Muse-Glimmer — ATEM XML markup declared by the chat template; the parser lifts the calls into the same structured tool_calls shape.
  • Muse Spark — the same ATEM XML calls, routed on the to= recipient header, plus a commentary channel.
  • MiniMax-M3.1 — namespaced XML: ]<]minimax[>[<tool_call> around one <invoke name="…"> per call, one element per argument, typed from the declared schema. On /v1/chat/completions, tool_choice required or a named function is grammar-enforced after </mm:think> and parallel_tool_calls: false allows one call.
  • DeepSeek V4.1 — spaced DSML (<｜DSML｜ calls>), which V4's unspaced form is not compatible with. On /v1/chat/completions a request-local grammar enforces the declared tools at the token level: tool_choice auto / required / none / a named function and parallel_tool_calls: false are all honoured, and unsupported schema assertions are refused with HTTP 400 before generation.
  • DeepSeek V4 — DSML markup: the system prompt teaches the syntax and carries one JSON schema per function, and the model answers with <｜DSML｜tool_calls><｜DSML｜invoke name="NAME"><｜DSML｜parameter name="key" string="true|false">value</｜DSML｜parameter>….
  • GLM 5.x — XML with per-argument tags: <tool_call>NAME<arg_key>k</arg_key><arg_value>v</arg_value>…</tool_call>. The function name follows the opening tag as bare text and every argument is its own key/value pair; values the template rendered with tojson are parsed back into numbers, arrays and objects.

Mistral 3, Hunyuan Dense and DiffusionGemma are not on this list: the first two render neither tool declarations nor tool results, and DiffusionGemma refuses requests that carry tools, so client tools, built-in skill/code tools and sub-agent delegation are not offered to them. Selected Agent Skill instructions are inlined as a no-tool fallback.

See Tool calling over HTTP for a complete request/response example and the continuation loop.
