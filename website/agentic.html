Agentic Work

TensorSharp.AgentHost turns a local model response into a bounded generate → inspect → run → repair → answer loop. It can load Agent Skills only when they are needed, work with files through four built-in code tools, run checks inside an OS sandbox, hand independent parts of a server request to bounded sub-agents, and return finished artifacts to an ordinary CLI, Web UI, Ollama, or OpenAI client.

What happens in one turn

  1. Advertise capabilities cheaply

    TensorSharp puts only each reachable skill's name and description in the prompt. A selected skill is preferred and made reachable; selection does not load its instructions.

  2. Load instructions on demand

    When a tool-capable model decides a skill applies, it calls skills_read(skill, "SKILL.md"). TensorSharp answers that built-in call in process, appends the result to the same conversation, and generates again.

  3. Do the work

    If the operator enabled --code-exec, the model can inspect, edit, create, patch, and test files in a request or chat workspace. Skill scripts can participate too, but only under their separate execution opt-in.

  4. Return an ordinary answer

    The client receives the final completion rather than TensorSharp's internal tool calls. A caller's own tools are never executed by TensorSharp; those calls are returned normally for the caller to service.

🎯

One loaded model, in-process tools, and bounded sub-agents. On the server's chat paths a tool-capable model can also delegate independent work to sub-agents that run on the same loaded model; the CLI runs a single agent. There is no interactive approval queue before each command. The operator grants or withholds skills, script execution, code execution, networking, and installation when the CLI or server starts; an internal tool then runs under that policy or refuses.

TensorAgent on iPhone and iPad

TensorAgent packages this local chat and agent experience as a .NET MAUI iOS/iPadOS app. The engine is statically linked as an iOS .xcframework and uses ggml_metal on physical devices, with ggml_cpu as the alternative there and the only backend in the simulator; MLX is not built for iOS. The app shares the host-neutral chat pipeline (TensorSharp.Chat) with the server, but serves the UI through an in-process loopback server because iOS has no ASP.NET Core runtime pack. What it shares is the API, not the document: the phone gets its own page, laid out for a thumb rather than a mouse and a wide window, bound to the same WebUiChatService and SkillsService routes.

Models download to the device with resume and SHA-256 verification; conversations survive app restarts; photos, camera, video, files, and dictation use the same chat attachment flow. Since iOS cannot start child processes, TensorAgent's shell, Python, and JavaScript integrations are runtime-backed and report their limits explicitly.

Three constraints a phone imposes that a desktop does not, and what the app does about each:

ConstraintWhat the app does
The screen goes away mid-answerGeneration belongs to a host-side manager, not to the WebView — WebKit suspends a page whose view left the window. A turn keeps running while you move to another screen in the app. When the app leaves the foreground the engine pauses between steps, because iOS forbids GPU work in the background; the turn keeps its place and its cache, resumes when the app is active again, and the page re-attaches to it.
The first message of a launch pays for the whole shared prefixThe state at the end of the prompt every chat shares is checkpointed to disk per model and restored at admission on the next launch. Measured on iPhone 17 Pro Max with Qwen3.5 9B: a 54 s cold first message becomes a 1.2 s warm-up and a ~0.6 s first message.
iOS jetsam kills without a stack or a messageThe engine's memory policy is sized against what jetsam charges — wired file pages count against the device, not the process — so caches start small and grow, a request reserves a bounded reply, and a memory warning releases what only serves the next request's speed.

The app targets iPhone and iPad (arm64, iOS 17.0 or later). It uses the scene lifecycle, which a build against the iOS 27 SDK needs in order to launch; the recorded physical-device runs are on iOS 26.6.1. Its built-in catalog — Gemma 4 E2B, E4B and 12B, Qwen3.5 9B, and the sideload-only, experimental Bonsai 8B and 27B — is offered on devices in the 12 GB memory tier and above. Several behaviors differ from the desktop hosts:

  • Speculative decoding is on by default — a draft head for Gemma 4 E4B and 12B when one was downloaded, n-gram lookup otherwise where the model supports speculation. Changing the setting applies to the running engine from the next reply.
  • Sub-agent delegation is on by default, with a switch (see below). Settings > Sandbox > "Sub-agents" turns it off from the next message, withholding the coordination tools as --no-multi-agent does; the limits stay at the host defaults, and the phone page shows no sub-agent panel.
  • Generated files open in Quick Look, with the share sheet as the fallback.
  • An “Ask TensorAgent” share extension brings a web page, photo, file, or text from another app into a chat, with presets such as Summarize, Key points, and Translate.

The same AgentAppHost also runs on macOS, Linux, and Windows. There, AgentExecutionMode.Auto (or Process) runs commands and skill scripts as native processes under the desktop OS sandbox instead of the embedded runtimes. When a networkHosts allow-list is set, that desktop backend refuses network-enabled launches rather than broadening access it cannot enforce.

See the TensorAgent README for build, simulator, device, and verification instructions.

Agent Skills and progressive disclosure

A skill is a directory containing a required SKILL.md plus any scripts, references, and assets its instructions need. TensorSharp follows the Agent Skills specification and can load published skill repositories without rewriting their layout.

pdf/
├── SKILL.md
├── scripts/
│   └── extract_tables.py
├── references/
│   └── forms.md
└── assets/
    └── template.pdf
TierWhat reaches the modelWhen
Metadataname + descriptionUp front for selected and discoverable skills. This is the normal prompt cost.
InstructionsThe complete SKILL.md bodyOnly after the model activates it with skills_read(skill, "SKILL.md").
Bundled filesReferences, scripts, and assetsPaths and sizes are indexed; content is fetched only through skills_read, paged at 48 KB.

The normal metadata block uses about 2% of the context window, clamped to roughly 1,024–10,000 tokens. The old behavior that inlined every selected body is off by default. A model family that cannot carry and parse tool declarations has no opportunity to call skills_read, so TensorSharp instead inlines selected skill bodies within a bounded fallback budget and does not advertise skills it cannot load.

The built-in skill tools are skills_list and skills_read. A third tool, skills_run, appears only with --skills-allow-exec. Script execution is off by default and remains separate from model-authored code execution.

Where skills come from

--skills-dir (repeatable) or TS_SKILLS_DIR names the roots explicitly. Without either, the CLI and server search every existing .agents/skills directory from the working directory up to the Git repository root, nearest first (outside a repository, only the working directory), plus the skills folder beside the binary, which is created if it is missing. The CLI searches that folder last. On the server it is also the upload directory, so it is always scanned, and scanned first: an uploaded skill wins a name clash, and it stays in the list even when --skills-dir or TS_SKILLS_DIR replaces the .agents/skills defaults. Personal or global skill folders are never imported implicitly.

Four code tools, off by default

--code-exec adds a patch-first coding surface. It does not require a skill, and merely installing or selecting a skill does not turn it on.

ToolPurposeImportant bound
read_fileRead real workspace bytes with line numbers.Bounded output; paths stay inside the workspace.
write_fileCreate a new file.Confined to the workspace; an existing path is refused, so existing files change through apply_patch.
apply_patchModify one file or multiple files by anchored hunks, including a single-line change; also create, rename, or delete files.Atomic: all hunks apply or none do.
shellRun tests, commands, and generated programs.Timeout and output caps; sandbox-or-refuse on supported hosts.

Failures are designed to be repairable. A diagnostic that identifies a regular source file in the workspace returns a bounded source excerpt and asks for the smallest apply_patch change before rerunning. Syntax checks, missing-import installation when allowed, and installed-library API hints reduce avoidable model rounds.

Workspace lifetime and artifacts

SurfaceWorkspace lifetimeResult
CLI / interactive chatPersistent for the process or chat session.One tool call can inspect or repair files written by an earlier call.
Bundled Web UIPersistent for that Web chat session.Live writing/running activity, bounded output, and generated-file download chips.
OpenAI and Ollama HTTP chatOne private workspace across every internal tool round in that request; deleted when the response finishes.Repairs work within a request, while separate requests remain stateless.
skills_run without code executionFresh per-call scratch directory, deleted on return.Scripts do not accidentally share state.

When code execution is enabled, a skill script shares the same request/chat workspace as the four code tools. The server copies produced files into its bounded artifact store; the Web UI exposes safe download links, and artifact responses are sent as attachments with content sniffing disabled.

Sandbox-or-refuse security model

Enabling execution is an operator decision, not a request field. On macOS and Linux, model-authored commands and opted-in skill scripts run with a workspace write boundary, an unreadable home directory, a scrubbed environment, and network denied by default. Paths are also checked in process before the OS sandbox is entered.

PlatformModel-authored codeSkill scripts
macOSsandbox-exec; refuses if confinement is unavailable.Default --skills-sandbox required; sandboxed or refused.
LinuxRequires bwrap 0.12.0 or newer; otherwise refuses.The same safe bwrap requirement under the default required mode.
WindowsNo filesystem/network sandbox is implemented. --code-exec-unconfined is required and intentionally grants the process's file and network reach.A job object bounds the process tree but not files or sockets. Default required refuses; --skills-sandbox preferred is the explicit weaker opt-in.
⚠️

Sandboxed does not mean a disposable VM. macOS deliberately retains access to shared /private/tmp and the per-user Darwin temp directory for compatibility, plus some local Unix IPC. Seatbelt restrictions pass to children and ordinary process groups are stopped, but a deliberately detached child can outlive the request; every tool result reports that gap. Linux shares parts of the host network namespace even while IP networking is denied. Every reported platform gap matters. Do not enable unconfined execution on a server other people can reach.

Network and package installation are separate opt-ins

OptionDefaultWhat it grants
--code-exec-allow-networkOffUnrestricted host IP networking for every model-authored command, including LAN/loopback services. It is not domain-filtered.
--skills-allow-networkOffNetwork for opted-in bundled skill scripts only. It does not affect shell.
--code-exec-allow-installOffHost-performed recognized pip/npm installs. The host reads and validates package names, uses prebuilt wheels / disabled npm scripts, and removes the install from the model's command.

--code-exec-packages, --code-exec-install-index, and --code-exec-install-domains constrain the host installer. They are not a security boundary after unrestricted command networking is enabled, because generated code can download an artifact directly. The script and code network switches are intentionally independent.

Browser automation: the Playwright skill

Browser “computer use” is a skill, not a runtime feature: there is no screen or mouse tool and no browser bridge. The playwright bundle in TensorAgent/skills drives a real browser through skills_run and a wrapper script that runs a pinned @playwright/cli with npx. Its instructions cover navigation, form filling, snapshots, screenshots, and data extraction, asking the user for missing information, and handing a headed persistent browser to the user for a login or CAPTCHA.

dotnet run --project TensorSharp.Server.Host -c Release -- \
  --model models/model.gguf --backend ggml_metal --host 127.0.0.1 \
  --skills-dir ./TensorAgent/skills \
  --skills-allow-exec --skills-allow-network \
  --code-exec --code-exec-allow-install --code-exec-allow-network

Besides those opt-ins it needs real Node.js, npm, and npx on the host. On macOS the skill has the model create .playwright/cli.config.json with write_file to turn off Chromium's own sandbox, because a process already confined by Seatbelt cannot start a second one; the outer Seatbelt sandbox stays on. It has been validated on macOS arm64 only, not on Linux or Windows. It is left out of the iOS app bundle, because iOS has no child processes or Node.js; TensorAgent/skills keeps it for the desktop hosts. Setup, account handoff, and recorded runs are in docs/playwright_agent.md.

Start an agentic session

Skills can be used without executing code:

dotnet run --project TensorSharp.Cli -c Release -- \
  --model models/model.gguf --backend ggml_metal \
  --skills-dir ./skills --skill pdf -i

Add the four code tools explicitly. This example keeps both command networking and package installation off:

dotnet run --project TensorSharp.Cli -c Release -- \
  --model models/model.gguf --backend ggml_metal \
  --skills-dir ./skills --skill pdf --code-exec -i

Or host the same loop for the Web UI and compatible APIs:

dotnet run --project TensorSharp.Server.Host -c Release -- \
  --model models/model.gguf --backend ggml_cuda \
  --skills-dir ./skills --code-exec

# Browser UI: http://localhost:5000/
# Liveness:   http://localhost:5000/health

On Linux, install bwrap 0.12.0 or newer first. On Windows, code execution remains unavailable unless the operator deliberately adds --code-exec-unconfined. Do not copy that Windows escape hatch onto a shared server.

Use skills from an ordinary HTTP client

The server must be started with a skills registry. A client then selects skills on the normal chat request; TensorSharp services its own skill/code calls internally and returns the completed response.

{
  "model": "local",
  "messages": [
    { "role": "user", "content": "Extract the tables and summarize the findings." }
  ],
  "skills": ["pdf"],
  "skills_discovery": false,
  "stream": true
}

skills_discovery defaults to true. Code execution has no per-request enable field: the operator either started the host with --code-exec or the four tools are absent. The agent loop allows 8 internal rounds by default, or 24 when code execution is enabled; --skills-max-rounds sets an explicit 1–64 bound.

Sub-agents: bounded delegation

On the server's chat paths — OpenAI /v1/chat/completions and /v1/responses, Ollama /api/chat/ollama, and the Web UI's /api/chat — a tool-capable model can hand independent parts of a request to sub-agents and combine their reports into one answer. Delegation is on by default, and the model decides whether to use it; nothing forces a spawn. It needs neither skills nor --code-exec: the five coordination tools are offered on their own.

ToolBehavior
spawn_agent(task_name, task, agent_type?)Starts a child and returns its ID immediately. agent_type is explorer (the default), reviewer, or worker.
wait_agent(agent_id?, timeout_ms?)Waits for one direct child, or for all of them when the ID is omitted: 10,000 ms by default, 60,000 ms at most. A timeout is not completion.
send_input(agent_id, message)Queues a follow-up for a running child at its next generation boundary, or starts another turn on a completed one.
close_agent(agent_id)Cancels a child and its descendants.
list_agents()Reports the direct children and their status.

Every child runs on the same loaded model with the parent's token limit, thinking mode, and sampling. It starts from the parent's system/developer instructions and its own self-contained task, not the parent's transcript or attachments, and it returns a bounded report. explorer and reviewer children are always read-only: besides the five coordination tools (so a child can delegate further, within --agents-max-depth), they get skills_list, skills_read, and read_file when the parent has it. A worker is read-only too unless the server was started with --agents-allow-worker-tools and its parent is the root or another mutable worker; it then gets the parent's enabled mutable tools, so delegation never widens permissions. A mutable worker shares the parent's workspace and sandbox, and read-only children read that same workspace; there are no Git worktrees or merging. Caller-owned tools are never passed to a child, and host tool calls anywhere in one request's tree run one at a time. Each child gets its own copy of the KV state rather than shared pages. Before the parent prefills, the host checkpoints the prefix it shares with its children, so a child can restore that prefix instead of computing it again.

Server optionDefaultRange and meaning
--no-multi-agentDelegation onTurns delegation off. TS_NO_MULTI_AGENT set to any value other than 0 does the same.
--agents-max-concurrent31–32 active descendants, not counting the root
--agents-max-count81–128 children per request tree
--agents-max-depth21–8 levels below the root
--agents-max-rounds81–64 tool rounds per child turn
--agents-max-generations481–1024 child generations per request
--agents-timeout180 s1–3600 seconds per child run
--agents-max-result-chars8000256–64000 characters per report
--agents-allow-worker-toolsOffLets worker children use the parent's enabled mutable tools

A request can opt out with "multi_agent": false. It cannot turn delegation on when the host has turned it off, raise a limit, or enable worker tools. While wait_agent runs, the Web UI's activity row carries an expandable panel with a live card for each sub-agent (task, status, current tool, result). OpenAI and Ollama responses carry only the parent's text. The CLI and Ollama /api/generate do not delegate. TensorAgent uses the host's default limits and has a "Sub-agents" switch in Settings (on by default) that turns delegation off from the next message.

The tools are offered only to families that render tool declarations and parse tool calls — not Mistral 3, Hunyuan Dense, or DiffusionGemma — and never on structured-output requests. There is no model-size gate. No latency, quality, or delegation-rate measurements are published. Delegation spends extra tokens and context, and whether it helps depends on the workload. Details: docs/multi_agent.md.

Model-family limits

The in-process loop requires a model family that can both carry tool declarations and parse tool calls. Families without that round trip receive selected skill instructions inline as a fallback, but are not offered the four code tools or the sub-agent tools; among the supported families that is Mistral 3, Hunyuan Dense, and DiffusionGemma. Qwen 3.8 Flash Next now completes the round trip. TensorSharp logs the limitation rather than silently pretending code execution is available.
